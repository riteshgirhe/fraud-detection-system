FRAUD DETECTION APP - RUN AND TEST GUIDE
========================================

PROJECT DOCUMENTATION
=====================

1. PROBLEM STATEMENT: FRAUD AND CLASS IMBALANCE
-----------------------------------------------
Payment fraud detection helps identify suspicious transactions early enough to
review, block, or investigate them. A useful system must distinguish unusual
fraudulent behavior from the much larger volume of legitimate activity while
keeping both missed fraud (false negatives) and unnecessary alerts (false
positives) in view.

Fraud labels are rare in real payment data: most transactions are legitimate.
The local PaySim dataset contains 8,213 fraud transactions out of 6,362,620,
or about 0.1291%. A model that always predicts "legitimate" would therefore
appear 99.87% accurate while detecting no fraud at all. Accuracy alone is not
a useful measure for this task. This project compares precision-recall behavior,
uses class-weighting and resampling experiments, and selects an operating
threshold on validation data.


2. SYSTEM ARCHITECTURE
----------------------

  User

   |
   | HTTP/JSON
   v
  FastAPI service
   |                    \
   | validated inputs    \ request/latency counters,
   v                      \ PSI/KS drift and feedback metrics
  Production pipeline      v
  (preprocessing +       Monitoring endpoints and dashboard
   XGBoost model)
   |
   v
  Fraud probability compared with threshold 0.995
   |
   +----> Decision returned to React
   |

The frontend supports individual and CSV batch scoring, history, monitoring,
and production model details. FastAPI validates transaction fields before
inference and returns the score, decision, model version, timestamp, and
latency. Operational request counters are held in process memory; prediction
records are persisted to data/predictions/predictions.jsonl.


3. DATASET
----------
Dataset: PaySim synthetic mobile-money transaction data. The project operates
on the local file data/raw/raw_data.csv. PaySim is a simulator-generated
dataset; the original PaySim work is described by Lopez-Rojas, Elmir, and
Axelsson, "PaySim: A financial mobile money simulator for fraud detection"
(2016). Confirm the specific download/distribution when citing a dataset copy;
this project does not record a download URL.

Rows:                  6,362,620
Fraud transactions:        8,213 (0.1291%)
Legitimate transactions: 6,354,407 (99.8709%)
Fraud-to-legitimate ratio: approximately 1 to 773

Raw columns:
  step              Simulation time step (hour index)
  type              Transaction category
  amount            Transaction amount
  nameOrig          Origin account identifier
  oldbalanceOrg     Origin balance before transaction
  newbalanceOrig    Origin balance after transaction
  nameDest          Destination account identifier
  oldbalanceDest    Destination balance before transaction
  newbalanceDest    Destination balance after transaction
  isFraud           Fraud target label (not accepted by inference API)
  isFlaggedFraud    Dataset-provided flag

The serving API accepts seven fields: step, type, amount, oldbalanceOrg,
newbalanceOrig, oldbalanceDest, and newbalanceDest. Account IDs and target
labels are not accepted. The selected model excludes nameDest-derived features
so training and API inference use the same available inputs.

The dataset is split in time order into training, validation, and test
segments. Training uses a bounded sample for workstation memory; validation
and test metrics use their full saved splits.

5. LIMITATIONS AND FUTURE WORK
------------------------------
Limitations:
- PaySim is synthetic. High scores on this dataset do not demonstrate the same
  performance on real customers, institutions, or changing fraud patterns.
- The 0.995 threshold was selected on validation data to maximize F2. It is an
  operating choice, not a universal fraud probability cutoff; costs, review
  capacity, and acceptable customer friction may call for another threshold.
- Repeated model selection and synthetic patterns can make validation/test
  performance optimistic. Production performance requires external,
  representative, independently labeled data.
- Request counts and latency percentiles are process-local and reset when the
  API restarts. JSONL transaction storage is a simple local persistence layer,
  not a production-scale database.
- The CSV uploader accepts simple comma-separated rows; quoted CSV fields with
  embedded commas are not a full CSV dialect implementation.

Future work:
- Validate and recalibrate the model with representative, privacy-approved
  real-world data and evaluate across time periods and customer segments.
- Revisit threshold selection using explicit false-positive and false-negative
  costs plus analyst review capacity; report calibration and operating curves.
- Add durable database storage, retention controls, authentication,
  authorization, rate limits, and deployment secrets management.
- Persist operational metrics and alerts outside the application process, and
  add drift-triggered review and a documented retraining/rollback process.
- Add robust CSV parsing, larger-scale batch processing, and accessibility and
  performance checks on target deployment devices.


RUN AND TEST
============

PROJECT LOCATION
----------------
C:\Data Science\ML\ML Project\Project 2\generated\AI Projects store\fraud-detection-mlops

The backend and frontend commands must be run from the project folder, not its parent.
Open two PowerShell terminals and leave both running while using the website.


1. START THE BACKEND
--------------------
In PowerShell terminal 1:

cd "C:\Data Science\ML\ML Project\Project 2\generated\AI Projects store\fraud-detection-mlops"
$env:FRONTEND_ORIGIN = "http://localhost:5173"
.\backend\start.ps1 -Port 8001

Wait for Uvicorn to report that it is running. Verify the API in a browser:

http://127.0.0.1:8001/health

The response should show status "ok" and model_loaded true.


2. START THE FRONTEND
---------------------
In PowerShell terminal 2:

cd "C:\Data Science\ML\ML Project\Project 2\generated\AI Projects store\fraud-detection-mlops\frontend"
$env:VITE_API_BASE_URL = "http://localhost:8001/api/v1"
npm run dev

Open the address printed by Vite, usually:

http://localhost:5173

Choose "Risk assessment" to score one transaction. You can use the "High-value
transfer" quick scenario to fill in the suspicious example below automatically.

TROUBLESHOOTING
---------------
If the website does not show model status as online:

1. Confirm both terminals are still running.
2. Confirm the backend is using port 8001 and the frontend command includes
   VITE_API_BASE_URL="http://localhost:8001/api/v1".
3. Visit http://127.0.0.1:8001/health and confirm it returns status "ok".
4. If you restart the frontend terminal, set VITE_API_BASE_URL again before
   running npm run dev.

API documentation is available at:
http://127.0.0.1:8001/docs
